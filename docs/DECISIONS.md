## ADR-014 - Docker-first scaffold

Accepted for local implementation on 18 September 2026 at the user's request. Use one multi-stage Node 24 container serving the React build and Fastify API, with SQLite in a Docker-managed named volume at `/data`. This resolves ADR-005's local demonstration data location without selecting a Windows user-specific directory. AI remains disabled; no provider or paid operation is introduced.

Compose publishes only to `127.0.0.1`; binding `0.0.0.0` inside the container does not approve LAN exposure. Run as non-root, drop capabilities, keep the application filesystem read-only and exclude everything from the build context except an explicit source/configuration allowlist. Never include token.txt, uploads, credentials or reference packs in an image.

Alternative: native per-laptop Node/npm installations and an approved host data directory. Docker adds image updates, an engine/virtualisation prerequisite, disk usage and volume backup work, but standardises builds across laptops. Git carries code and the lockfile, not Docker volumes or saved exercises. A new clone starts a separate local dataset unless a backup is transferred and restored. Do not remove volumes or overwrite data as part of ordinary startup. Build/test portability is only established once the actual container checks pass.

## ADR-015 - Track-neutral product naming

Accepted on 19 September 2026 at the user's direction. Name the overarching product "AI-assisted TTX Platform" ("TTX Platform" in the application). Technical and operational are separate exercise tracks with the existing ownership split, not competing product names. Use neutral branding in the browser title, shared header, sign-in, startup message and architecture illustration. Retain explicit technical labels for the current track, technical content, RACI and the user's responsibilities.

This supersedes the earlier product-framing implication in ADR-012 and the baseline that the workstreams do not belong to one overarching platform; ownership, current technical-workstream acceptance criteria and the single-track first draft are unchanged. Detailed operational implementation and integration remain to be agreed, not silently implemented by a rename. Alternative: keep "Technical TTX" as the product name, which incorrectly excludes the other worker's track. Maintenance cost is consistency across UI, documents and diagrams; browser checks cover neutral branding alongside the explicit technical-track label. No schema, storage, dependency or deployment change is needed.

## ADR-016 - ENISA-adapted exercise flow

Accepted for planning on 22 September 2026 following the user's request to apply the reviewed flow changes, including the SVG, while they draft the readiness specification later. Use ENISA's February 2026 methodology as an adaptable lifecycle reference. This is not a claim of ENISA compliance, adoption of EU-specific duties or a requirement to implement every national-exercise deliverable.

Move purpose, track, audience and initial scope ahead of detailed exercise-specific intake. Keep a reusable organisation profile separate from the exercise plan, scenario assumptions and objective-dependent readiness decisions. Support documents, guided answers and reused reviewed context; missing files do not automatically establish missing capabilities. Add explicit package review, participant briefing/run readiness, bounded coached play, debrief, reviewed AAR and owned improvement actions. Requirements are in PROJECT; design and source mapping are in architecture.

This supersedes the intake-before-track ordering in the 18 September flow and the preparation order of the 20 September storyboard. It preserves ADR-003's deterministic first slice, ADR-004's approval controls and ADR-013's five injects/two answers/no initial scenario branching. Report first-attempt success per inject rather than claiming wholly unaided performance after earlier coaching. Both platform tracks remain discussion-based.

Alternative: profile until generically "ready" before deciding what to exercise. Rejected because information needs and acceptable uncertainty depend on objectives. A separate organisation-profile maintenance journey may still collect information before an exercise exists. Maintenance cost: version and bind profile, plan, criteria and readiness decisions; keep diagrams and planned screen order aligned. No application migration, new dependency or operational-track implementation is authorised by this documentation change.
